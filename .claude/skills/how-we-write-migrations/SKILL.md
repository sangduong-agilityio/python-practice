# How We Write Migrations

This skill defines the non-negotiable process for introducing database schema changes to the `task-management-api` repository.

## 1. Pre-Flight Checklist
Before touching any models:
1. Verify the current database revision:
   ```bash
   alembic current
   ```
2. Verify there are no diverging migration branches:
   ```bash
   alembic heads
   ```

## 2. Generating the Migration
1. Modify the SQLAlchemy model in `app/models/`.
2. Generate an autogenerated revision with a clear, imperative description:
   ```bash
   alembic revision --autogenerate -m "add_<column>_to_<table>"
   ```
3. **NEVER trust autogenerate blindly.** Open the newly created file in `alembic/versions/` and inspect:
   - Ensure the `upgrade()` function only touches expected tables and columns.
   - Verify that all Enum changes have explicit drop/create type guards if using Postgres.
   - Ensure foreign keys have indexing on the child table.

## 3. Zero-Downtime Safety Rules
- **Adding Columns:** Never add a `nullable=False` column without a `server_default`. If a default is needed, provide it or execute in two phases.
- **Dropping Columns:** Never drop a column in the same release that stops reading it. Deprecate first in code, deploy, then drop column in a subsequent migration.
- **Renaming Columns:** Do not rename directly. Add new column -> dual-write -> backfill -> read new column -> drop old.

## 4. The Bidirectional Verification Loop
Always test both upgrade and downgrade before committing:
1. Apply the migration:
   ```bash
   alembic upgrade head
   ```
2. Verify rollback capability:
   ```bash
   alembic downgrade -1
   ```
3. Re-apply to head:
   ```bash
   alembic upgrade head
   ```
4. Run the full test suite (CLAUDE.md requires it to be green):
   ```bash
   pytest
   ```
